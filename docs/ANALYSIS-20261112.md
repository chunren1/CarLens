## 1. 项目背景与定位

### 1.1 题目与目标

- 论文题目：《新能源汽车在线配置与报价系统的设计与实现》
- 项目形态：比亚迪 BYD 品牌演示站（非官方），单品牌、直营模式、在线配置、透明报价、模拟下订与支付。
- 目标用户：
  - 购车者：不知道买什么、怕配置选错、怕价格不透明。
  - 运营/销售：维护车型价格、跟进试驾线索、处理订单与内容。
  - 评委/答辩老师：3 分钟内看懂“这系统能做什么、技术点在哪”。
- 明确非目标：真实支付、真实车源、真实物流、多品牌聚合、二手车、金融风控、SSR/SEO。

### 1.2 为什么这个定位成立

1. **单品牌才能把配置器做深**：聚合平台只能列参数，单品牌才能把版本、车漆、轮毂、内饰、选装、规则、价格、订单串成闭环。
2. **配置与报价是天然的技术载体**：价格公式、规则约束、服务端权威、快照一致性、订单状态机，都能写成论文的技术章节。
3. **演示性强**：从首页到支付成功可以在几分钟内走完，适合答辩现场。

### 1.3 项目边界判断

| 范围 | 判断 |
|---|---|
| 单品牌官网 | 合理，符合题目与老师要求 |
| 配置器 + 报价 | 核心，做得最深 |
| 模拟支付 + 订单 | 合理补充，不触碰真实资金 |
| 后台运营 | 合理，能讲“闭环” |
| 试驾/金融/对比/向导 | 加分项，但增加维护面 |
| 3D 配置器 | 已退出主流程，作为历史技术点保留；不应再作为主线承诺 |
| 配置分享/推荐算法/真实支付 | 未实现或仅半成品，论文中不要写成已完成 |

## 3. 技术架构分析

### 3.1 全局架构

    浏览器（Vue 3 SPA）
      │ HTTPS https://ziphare.me/（Cloudflare 边缘 + 隧道）
      ▼
    cloudflared → nginx :80
      ├── /assets /images /models /basis → /var/www/wangshu（静态）
      ├── /api/ → 127.0.0.1:3100（Fastify）
      └── 其它 → /index.html（SPA fallback）

    Fastify API（systemd: wangshu-api）
      ├── routes（health/models/quote/stores/orders/payments/auth/test-drives/news/admin）
      ├── repositories（catalog/orders/settings/stores）
      ├── db（Drizzle + better-sqlite3 + migrations）
      └── /opt/wangshu/data/wangshu.db（WAL）

    packages/shared
      ├── types.ts    共享 DTO
      └── pricing.ts  价格与规则引擎（纯函数）

### 3.2 技术选型评估

| 选型 | 作用 | 优势 | 局限/风险 | 判断 |
|---|---|---|---|---|
| Vue 3 + TypeScript | 前端 SPA | 组合式 API、类型友好、生态成熟 | 无 SSR/SEO；首屏依赖 JS | 适合演示，合理 |
| Vite | 构建/开发服务器 | 快、路由懒加载、体积小 | 生产仍需 nginx 配合 | 合理 |
| Pinia | 状态管理 | 配置器/登录态清晰 | 全局 store 跨路由残留需注意 | 合理 |
| Vue Router | 路由 | 24 个路由、懒加载 | 无路由级权限守卫 | 合理 |
| Fastify 5 | API 框架 | 轻、快、插件化、错误处理集中 | 需自己补限流/安全头 | 合理 |
| Drizzle ORM | 数据访问/迁移 | 类型安全、SQL 可控、迁移可重复 | 复杂查询仍需手写 | 合理 |
| SQLite + better-sqlite3 | 数据库 | 零运维、单文件、备份简单 | 单机、并发有限、无多实例 | Demo 合理，生产需评估 |
| Zod | 运行时校验 | 入参校验、错误统一 | 只覆盖边界，不替代业务规则 | 合理 |
| tsx | 生产运行 TS | 无需构建、启动直接跑源码 | 启动稍慢、生产依赖运行时 | Demo 可接受 |
| systemd + nginx | 部署 | 简单、稳定、资源占用低 | 无容器编排、无自动扩缩 | 适合单机演示 |
| Cloudflare Tunnel | 入口 | 无需暴露 443、证书自动 | 依赖 CF、链路多一跳 | 合理 |

### 3.3 架构亮点

1. **服务端权威定价**：`POST /quote` 与 `POST /orders` 共用 `calculateQuote()`，前端只传选项 ID。价格与合法性不可能被前端绕过。
2. **共享纯函数价格引擎**：`packages/shared/src/pricing.ts` 无 IO、无数据库依赖，入参 catalog + settings，出参完整 QuoteResult；可单测、可解释、可写论文。
3. **规则数据化**：`option_rules` 用 `ifOption / requiresOption / excludesOption / minTrimRank` 描述约束，新增规则不必改代码。
4. **报价即快照**：订单落库 `config_json` 存完整 QuoteResult，历史订单可复现，不随商品调价漂移。
5. **共享类型**：`packages/shared/src/types.ts` 同时被 API 与 Web 引用，DTO 漂移风险低。
6. **错误信封统一**：`ApiError / QuoteError / ZodError / Fastify validation / 未知错误` 统一成 `{code,message}`。

### 3.4 架构层面的结构性问题

| 问题 | 说明 | 影响 |
|---|---|---|
| 后台未走仓储层 | `routes/admin.ts` 直接 `app.db.select/update`，而 orders 走 `repositories/` | 业务规则散落，后续改价/审计难收口 |
| `configs` 表空置 | 表、`leads.configId`、`orders.configId` 全流程未使用 | 论文写“18 张表”时有 1 张死表；配置分享无法自圆 |
| 多车型硬编码 | 首页参数、向导、对比、页头/页脚 CTA 固定 r1/s7 | 与“新增车型只需海报+seed”的架构承诺冲突 |
| 快照无版本 | `config_json` 直接 `JSON.parse as QuoteResult` | QuoteResult 结构变化后旧订单可能解析失败 |
| 单机 SQLite | 无读写分离、无多实例、无连接池 | 演示足够；高并发/多实例需 PostgreSQL |
| 无 CI/CD | 手工 rsync + restart | 发布质量依赖人，回滚成本高 |

## 4. 核心机制分析

### 4.1 价格引擎

实现位置：`packages/shared/src/pricing.ts`。

    裸车价     = 版本价 + 车漆价 + 轮毂价 + 内饰价 + 选装包价
    全额购置税 = 裸车价 ÷ 1.13 × 10%
    减免额     = min(全额购置税 × 50%, 15,000 元)
    实缴购置税 = 全额购置税 - 减免额
    保险       = round10(裸车价 × 2.2% + 950 元)
    上牌       = 500 元
    落地价     = 裸车价 + 实缴购置税 + 保险 + 上牌
    定金       = 5,000 元（settings 可配）

**优点**：

- 金额统一 integer 分，避免浮点误差。
- 税费/保险/上牌/定金全部进 `settings` 表，可配置、可讨论政策变化。
- 规则引擎与价格计算分离：先校验规则，再算钱。
- 纯函数，容易写单测；5 个共享测试覆盖基础价、规则、减免上限。

**可改进**：

- `rangeKm` 直接 `trim.rangeKm + wheel.rangeDelta`，没有下限保护。
- `settings` 值没有合法性约束（如 `taxDivisor=0` 会除零）。
- `warnings` 字段目前恒为空，可用来提示“续航下降/配置冲突已自动处理”等。

### 4.2 规则引擎

`optionRules` 支持四类约束：

| 字段 | 含义 | 示例 |
|---|---|---|
| `ifOption` | 命中哪个选项 | `wheel:3` |
| `requiresOption` | 必须同时选什么 | 选装包 A 需要选装包 B |
| `excludesOption` | 不能同时选什么 | 某车漆与某内饰冲突 |
| `minTrimRank` | 最低版本等级 | 21 英寸轮毂需性能版 |

**评价**：这是项目最有“系统设计”味道的部分，适合写论文。当前只用了 `minTrimRank` 一条规则，`requiresOption / excludesOption` 没有种子数据与测试，答辩时如果被问“这两类规则真的能用吗”，需要补数据或明确说“引擎支持、Demo 未配置”。

### 4.3 订单与支付

状态机：

    pending_payment --pay--> paid --confirm--> confirmed --deliver--> delivered
          |                    |
          +------cancel--------+--> cancelled

**做得好的**：

- 支付幂等：已支付直接返回，不重复写 payments。
- 取消幂等：已取消再取消返回当前订单。
- 支付/取消放在事务里。
- 后台状态迁移集中校验，非法迁移 409。
- 订单号含上海日期 + 随机 hex，冲突重试。

**需要补的**：

- 支付接口没有订单归属校验（详见审查报告 SEC-2）。
- 下单没有幂等键，重复提交会生成多笔订单。
- 已支付订单被后台取消后没有退款记录，UI 仍显示“已支付”。
- 订单快照无版本号。

### 4.4 鉴权与会话

- 注册：scrypt + 随机盐，密码不存明文。
- 会话：32 字节随机 token，数据库存 SHA-256；cookie httpOnly + SameSite=Lax；生产 Secure。
- 管理员：`users.role = "admin"`，后台路由统一 `requireAdmin`。
- 缺口：无改密/找回密码/邮箱验证；无限流；默认管理员口令公开；过期 session 不清理。

- **首屏**：优秀。49.31 KB gzip JS，远低于 300 KB 预算。
- **图片**：车型图 25–100 KB WebP，海报 52–173 KB WebP，懒加载；合理。
- **3D 资源**：11 MB glb + 580 KB basis 仍部署但零引用，属于无效体积。
- **API**：数据量小，SQLite 足够；后台列表有 N+1，但演示规模无感。
- **缓存**：静态 assets 30 天 immutable；HTML 没有显式 no-cache；公共 GET 无缓存头。

### 5.5 安全判断

一句话：**设计正确，运维已上 HTTPS，但公开环境的“人和默认值”没管住**。

- 正确：scrypt、httpOnly/SameSite/Secure、会话哈希、参数化 SQL、无 v-html、服务端定价、后台角色校验。
- 严重：默认管理员口令公开且无改密；支付接口越权；登录/下单/试驾无限流；seed 可清库。
- 次要：无 CSP、www/apex 会话不共享、订单号 32 位且进日志、脚本硬编码口令、无 noindex。

### 5.6 测试判断

- 后端测试是项目最扎实的工程资产之一。
- 但测试集中在“正常路径 + 价格规则”，缺少“越权、限流、幂等、并发、前端交互”这五类最容易被答辩追问的用例。
- 本轮临时测试一跑就发现支付越权，说明**不是测试写得少，而是授权矩阵没被测**。

## 6. 项目管理分析

### 6.1 版本控制

当前仓库只有 7 个 commit，且全是文档；整个应用（apps/、packages/、deploy/、scripts/）都是 untracked。这是项目最大的**非代码风险**：

- 无法回滚到“昨天能跑的版本”。
- 无法用 diff 复盘“这次改了什么”。
- 无法接 CI。
- 换机器/重装/误删都可能丢代码。

**建议**：先提交当前可运行基线，再按模块分批提交；不要等“全部改完”才提交。提交顺序可以是：

1. 根配置 + 共享包
2. API（schema/migrations/repositories/routes/tests）
3. Web（lib/stores/components/pages/styles）
4. deploy + scripts
5. docs

### 6.2 文档体系

优点是“文档很多”，缺点是“文档之间不一致”。建议把文档分成三层：

| 层级 | 文档 | 维护策略 |
|---|---|---|
| 唯一真相源 | `docs/status.md`、`docs/DEPLOY-STATE.md` | 每次发布更新；其他文档引用它 |
| 设计/论文底稿 | `docs/design.md`、`docs/architecture.md` | 升 v1.0，按现状重写；与代码同步 |
| 过程材料 | `docs/REVIEW-*.md`、`screens/`、`demo-runbook` | 标注日期与适用范围，允许过期 |

### 6.3 交付与运维

- 部署链路：本地构建 → rsync → systemd restart → 健康检查；简单直接。
- 已做：HTTPS、HSTS、Secure cookie、每日备份、Restart=always、nginx 路由修复。
- 缺：发布前备份、回滚目录、rsync --delete、HTML no-cache、监控告警、备份异地、恢复演练。

### 6.4 风险矩阵

| 风险 | 概率 | 影响 | 优先级 | 处理 |
|---|---|---|---|---|
| 默认管理员口令被利用 | 高 | 高 | P0 | 立即换口令、删文档口令、加保护 |
| 支付越权/PII 泄露 | 中 | 高 | P1 | 加归属校验、补测试 |
| 误跑 seed 清库 | 中 | 高 | P1 | 生产拒绝、备份、拆命令 |
| 答辩现场旧口令/旧数据 | 中 | 中 | P1 | 演示前重置并验证 |
| 文档与实现不一致被追问 | 高 | 中 | P1 | 重写 design/AGENTS 关键章节 |
| 代码丢失/无法回滚 | 中 | 高 | P1 | 立即 Git 提交 |
| 新增车型出现错误参数 | 中 | 中 | P2 | 去硬编码 |
| 依赖/镜像审计缺失 | 低 | 中 | P3 | CI 中加 audit |

## 7. 优势、短板、机会、风险

### 7.1 优势（答辩可讲）

1. **完整闭环**：不是“配置器 Demo”，而是配置→报价→下订→支付→订单→后台。
2. **服务端权威定价**：前端只传 ID，价格与规则服务端算，安全性/一致性可讲。
3. **数据化规则引擎**：规则表 + 纯函数求值，新增约束不改代码。
4. **报价快照**：订单冻结配置与价格，历史可复现。
5. **真实部署**：HTTPS、Cloudflare、nginx、systemd、SQLite 备份，不是只跑 localhost。
6. **设计系统**：白底 + BYD 红 + 中文衬线 + 等宽数字，视觉统一。

### 7.2 短板（答辩前要补）

1. **安全边界**：默认口令、支付越权、无限流、seed 清库。
2. **文档一致性**：design/AGENTS/architecture 与实现冲突。
3. **可扩展性**：多车型硬编码；后台未走仓储层；configs 死表。
4. **工程流程**：未入 Git、无 CI、无 lint、无前端测试。
5. **可访问性细节**：轮播无暂停、灯箱无焦点陷阱。
6. **业务细节**：重复下单、过去时间试驾、收入口径、已支付后取消展示。

### 7.3 机会（论文/后续）

- 论文可以把“价格引擎 + 规则引擎 + 快照一致性”写成核心章节，而不是流水账写页面。
- 可以补“威胁模型与安全设计”章节：认证、会话、越权、限流、CSRF/XSS、CSP。
- 可以补“性能预算与实测”章节：首屏 49 KB、图片 WebP、路由懒加载、3D 不加载的取舍。
- 可以补“部署与运维”章节：单机 SQLite 的适用边界、备份/恢复、HTTPS 链路。
- 后续产品化：配置分享、预约管理、后台完整 CRUD、真实支付（超出毕设范围）。

### 7.4 风险（不要踩）

- **不要在论文/答辩中声称已实现**：3D 配置器、配置分享、推荐算法、argon2id、限流、Origin 校验、订单仅本人可支付。这些要么未做，要么与实现不符。
- **不要把“演示环境”当成“生产系统”**：默认口令、假数据、模拟支付必须在页面上讲清楚。
- **不要继续加功能**：当前短板在“收口”，不在“铺量”。

## 8. 改进建议

### 8.1 答辩前（最高优先）

1. **换管理员口令**：数据库改强随机；删除 `docs/status.md` 与脚本中的口令；确认旧口令失效。
2. **修支付越权**：`pay` 加归属校验，与 `get/cancel` 共用；补一条跨用户测试。
3. **演示数据重置**：确认订单/线索/新闻是想要的状态；备份数据库；演示前 10 分钟跑一遍主旅程。
4. **文档收口**：至少把 `design.md` 的 3D/分享/限流/argon2id/Element Plus 段落改成现状；把 `AGENTS.md` 的 v0.2/暗色令牌改掉。
5. **Git 提交**：先把当前可运行版本提交，答辩前不再裸奔。

### 8.2 上线前（高优先）

1. 限流（登录/注册/下单/试驾）。
2. seed 生产保护 + 发布前自动备份。
3. 收入口径改为 payments 或改标签。
4. 部署 rsync --delete、HTML no-cache、安全头入库、www→apex 跳转。
5. 备份异地 + 恢复演练 + 监控告警。

### 8.3 长期（锦上添花）

1. 下单幂等 + 成功后清快照 + 下订前复核价格。
2. 试驾日期/容量校验；配置器 loading 时禁用操作。
3. 向导 seats/预算、首页新闻/参数、对比/页脚 CTA 去硬编码。
4. 轮播暂停/减少动效、灯箱与抽屉焦点管理。
5. 拆分 AdminPage；加 ESLint/Prettier/CI；补前端测试与 Playwright。
6. 清理 3D 资源/死代码/一次性脚本/tmp 目录。

### 8.4 建议的“答辩叙事”

**推荐讲法**：

> “这是一个单品牌新能源汽车官网 + 在线配置与报价系统。核心不是页面，而是服务端权威定价：用户只选 ID，价格与规则在服务端算；规则用数据表描述，新增约束不改代码；下单时把完整报价冻结成快照，历史订单可复现；最后用模拟支付和订单状态机把闭环走完。”

**不建议讲法**：

> “我们做了 3D 配置器、配置分享、智能推荐、真实支付、高并发架构。”——这些要么没做，要么没验证，容易被追问翻车。

## 9. 结论

### 9.1 项目价值

- 对答辩：这是一个“能跑、能演示、有技术点、有部署”的完整作品，明显高于“只有页面”的毕设。
- 对论文：价格引擎、规则引擎、快照、状态机、鉴权、部署都能写成独立章节，素材充足。
- 对个人：已经具备全栈闭环、服务端安全意识、部署运维意识；下一步补的是“工程流程”和“安全收口”。

### 9.2 一句话总结

**功能上是一个完成度很高的毕设，工程上是一个“只差最后一公里”的项目：把默认口令、支付越权、限流、Git 和文档这五件事收口，它就从“能演示”变成“能交付”。**
