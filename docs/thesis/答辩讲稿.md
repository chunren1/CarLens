# 车鉴 CarLens · 答辩讲稿与问答

> 配套：docs/thesis/车鉴CarLens-答辩PPT.pptx（14 页）
> 建议时长：8–10 分钟；PPT 备注里也有逐页提示。

## 0:00–0:35 封面

各位老师好，我是计算机科学与技术专业的学生，毕业设计题目是“车鉴 CarLens”多品牌汽车配置聚合与在线报价平台的设计与实现，指导教师是高乐副教授。下面从选题、设计、实现和测试四个方面汇报。

## 0:35–1:10 汇报结构

汇报分四部分：先说明多品牌选车的问题，再讲系统架构、数据模型和计价设计，然后讲配置器、订单、换色和移动端实现，最后给测试结果、不足和演示地址。

## 1:10–1:50 问题与目标

品牌官网各自为战，配置器、选装规则和报价口径不统一；用户在同一预算下跨品牌比较，需要反复切页面、手工算落地价。3D 配置器效果依赖逐车建模，成本很高，纯海报又缺少配置反馈。本课题要回答三个问题：怎样统一目录、怎样保证价格一致、怎样控制展示成本。

## 1:50–2:40 研究目标与边界

目标可以概括为“聚合、配置、报价、交易、展示、保障”六个词：10 个品牌、20 款车型、45 个版本、260 条选装关系；版本、车漆、轮毂、内饰和选装包联动；服务端用整数分重算；下订、模拟支付和订单状态闭环；共享 3D 模型加 2D 海报；限流、CSP、输入校验和移动端适配。

边界要说清楚：价格、库存、门店和支付都是毕业设计演示数据，支付是模拟网关，不产生真实扣款；3D 模型只做选装示意，不是具体车型的精确还原。

## 2:40–3:30 总体架构

系统采用前后端分离。浏览器访问 nginx，静态资源由 nginx 返回，/api 反向代理到 Fastify。前端是 Vue 3 单页应用，后端用 Fastify 5、Zod、Drizzle ORM 和 SQLite。这样目录、计价和页面可以独立演进，3D 和配置器代码也能按需加载。

## 3:30–4:20 数据模型

数据模型围绕品牌、车型、版本、配置项和订单。车型表保存品牌、级别、续航、起售价；版本表保存版本价格；车漆、轮毂、内饰和选装包用共享字典；车型选装关系保存该车型下的价格和可用性；选装规则表达“21 英寸轮毂需要高配”等约束。订单保存配置快照，历史订单不会因为后续调价而失真。

## 4:20–5:10 配置器

配置器左侧展示、右侧选择，Pinia 管理状态。3D 用共享的 s7.glb，材质联动车漆和轮毂；2D 模式不加载 three.js 和 GLB，直接显示海报，弱网和移动端更稳定。这个设计是用“示意”换成本，后面不足部分会说明。

## 5:10–6:00 服务端计价

所有金额以分为单位。裸车小计由版本、车漆、轮毂、内饰和选装包相加；购置税、减免、保险、上牌和定金按统一公式计算。前端只展示，服务端重新读取车型和选装关系后计算；下单时再次复算并保存快照。以汉 EV 默认配置为例，落地价是 193,165.75 元。

## 6:00–6:45 订单与安全

订单号是“WS + 日期 + 8 位随机十六进制”。下订引入 Idempotency-Key：同一个 key 重试返回原订单，不同手机号复用同一 key 返回 409；数据库唯一索引兜底并发。支付也做了幂等，重复支付不会重复写 payments。接口还有限流、Cookie 会话、Zod 校验和 CSP。

## 6:45–7:20 换色与移动端

2D 换色没有用生成式整图重绘，而是做 mask 内的确定性 Lab 重映射，避免轮毂、车标和车牌被重画。当前海豹和汉 EV 各完成 5 色，非漆面 MAE 0.93–1.07；其他车型回退封面。移动端做了 390 和 360 宽度专项审计，修掉了轮播圆点溢出和对比表格只能看第一列的问题。

## 7:20–8:00 测试结果

API 测试 11 个文件、44 项全部通过，覆盖目录、计价、订单、支付、试驾、认证、后台和限流；vue-tsc 和 vite build 通过；移动端 390 宽度 15 个页面无横向溢出。线上通过健康检查和关键路径验收。

## 8:00–8:40 创新点与不足

主要工作是统一多品牌目录、服务端统一计价、共享 3D 加 2D 降级、确定性换色和订单幂等。不足也要主动说：3D 模型全系共用，只作示意；换色只完成 2 款；SQLite 单机，未验证高并发；真实支付、库存和金融没有接入；品牌仍是车型字段，没有拆品牌表。

## 8:40–9:20 演示与结束

线上地址是 https://ziphare.me/。演示路径是车型矩阵、配置器、报价、下订、模拟支付和后台。我的汇报到这里，请各位老师批评指正。

## 常见问题

1. **为什么不用 Spring Boot？**
   本项目是 TypeScript monorepo，前端、后端和共享计价类型使用同一语言，减少字段不一致；Fastify 轻量、启动快，适合演示规模。若换 Spring Boot，业务逻辑可以迁移，但共享类型和开发效率会下降。

2. **3D 模型为什么所有车共用？**
   逐车高精度建模成本过高，毕业设计时间有限。共享模型用于展示车漆、轮毂和视角交互，车型差异由封面海报和配置数据表达；这是明确的取舍，不是把共用模型说成精确还原。

3. **价格公式是真实政策吗？**
   不是。公式和税率是演示规则，目的是验证“服务端统一重算、配置快照、不可前端改价”的架构；真实业务需要按品牌和地区配置税率、补贴和保险规则。

4. **幂等键能解决并发吗？**
   请求先按 key 查，插入时唯一索引兜底；并发冲突时捕获唯一约束再查一次，返回已存在订单。测试覆盖了重放和不同手机号复用两种情况。

5. **为什么用 SQLite？**
   演示规模数据量小、单机部署简单、备份就是文件拷贝；代价是高并发和分布式能力弱。后续可以替换 MySQL/PostgreSQL，Drizzle 的迁移和 repository 层可以复用。

6. **换色图是 AI 生成的吗？**
   当前采用确定性 Lab 域重映射，不是整图生成；这样轮毂、车灯、车牌和背景不会漂移。代价是只能做颜色变化，不能生成新纹理，而且需要人工检查 mask。

7. **系统安全做了什么？**
   密码哈希、httpOnly Cookie、登录/下单/试驾限流、Zod 输入校验、订单归属校验、CSP、X-Frame-Options、Referrer-Policy 和 Permissions-Policy；后台接口在服务端再次校验角色。

8. **测试覆盖率多少？**
   没有做覆盖率百分比，重点是关键路径：目录、计价、订单、支付、试驾、认证、后台和限流；共 44 项 API 测试。后续可以补前端组件测试和端到端用例。

9. **创新点是什么？**
   把多品牌目录、统一计价、共享 3D/2D 展示和交易安全放在同一套系统里；不是单点算法创新，而是工程整合和取舍。

10. **后续怎么扩展？**
    补更多车型和换色图、逐车 3D 或车系级模型、品牌表、真实库存/金融/支付、压测和监控，以及换色图的后台审核入库。
