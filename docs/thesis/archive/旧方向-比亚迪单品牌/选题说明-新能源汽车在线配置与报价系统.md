## 二、选题背景与要解决的问题

新能源汽车普遍采用直营/线上下单模式，用户需要在官网完成“选车型—选版本—选车漆/轮毂/内饰/选装—看落地价—下订”的完整链路。与普通商品相比，汽车配置有三个特点：

1. **配置组合多**：版本、车漆、轮毂、内饰、选装包之间存在互斥、依赖和版本门槛，不能简单当成 SKU 列表；
2. **价格构成复杂**：裸车价之外还有购置税、保险、上牌等费用，用户看到的“落地价”必须可解释、可复算；
3. **前后端容易不一致**：前端展示价、报价单、订单快照如果各自计算，改价或刷新页面后就会出现“同配置不同价”。

现有同类毕业设计多集中在“汽车商城/汽车租赁/汽车资讯/选车推荐”，重点在商品展示或 CRUD；本项目把问题收窄到**配置约束 + 服务端权威报价 + 订单快照一致性**这条链路，并用可运行的官网验证。系统不止停留在配置和报价，还把报价接上下订、模拟支付、订单跟踪与后台处理，形成官方直营的“卖车”闭环。

## 三、主要研究内容

1. **业务建模**：建立车型、版本、车漆、轮毂、内饰、选装包、门店、订单、支付、试驾线索等数据模型；把“配置项—车型—价格—规则”组织成可查询的目录。
2. **配置规则**：实现选装包去重、选项归属校验、版本门槛（如 21 英寸轮毂需搭配高配）、互斥/依赖规则；非法组合在提交报价前直接拒绝并给出可读提示。
3. **服务端定价引擎**：以前端只提交选项 ID、服务端重新加载目录并计算为原则；按“裸车 + 购置税 + 保险 + 上牌”输出逐项报价，金额统一用整数分，避免浮点误差。
4. **订单一致性**：下单时把车型、版本、颜色、选装、价格快照写入订单；支付接口幂等；订单状态机覆盖待支付、已支付、已确认、已交付、已取消，用户只能取消待支付订单。
5. **展示与交互**：首页做左文右图车型轮播，配置器用高清车型海报替代粗糙 3D 车模，保留 3D 代码作为技术储备；完成 1440/1024/390 三档响应式适配。
6. **测试与部署**：API 自动化测试 38 项；Web 类型检查与构建；HTTPS 部署、Cloudflare 隧道、systemd、SQLite 备份。

## 四、技术路线与工作量

- 前端：Vue 3 + TypeScript + Vite + Pinia + Vue Router；不引组件库，手写设计系统。
- 后端：Node.js 24 + Fastify 5 + Drizzle ORM + SQLite（better-sqlite3）+ Zod。
- 共享层：TypeScript 类型与定价引擎，前后端共用金额/规则定义。
- 测试：Vitest；9 个测试文件、38 项 API 测试。
- 部署：Cloudflare 隧道 → nginx → systemd → SQLite；Let's Encrypt 证书，HTTP 301 到 HTTPS。
- 规模：18 张表、10 个路由模块、24 个前端页面；已上线 https://ziphare.me/。
- 3D：three.js/GLTF/KTX2 配置器做过一版，因车模精度和加载成本改为官方海报；代码保留，作为技术点写在论文中，不作为演示主路径。
