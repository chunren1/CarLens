# 毕业论文写作方案

> 依据：广州华立学院《本科生毕业论文（设计）撰写规范》（2026-10）、书写模板，以及项目现状（2026-11-12，Demo v0.6）。
> 结论：题目建议保持《新能源汽车在线配置与报价系统的设计与实现》；论文按“系统实现型毕业设计”写，正文目标 12000 字左右，不要写成产品说明书。

## 1. 题目怎么定

**主选：《新能源汽车在线配置与报价系统的设计与实现》**（20 字）。

理由：和系统、开题、答辩完全对应；不出现“比亚迪”商标；配置与报价是两个能写深的技术点；20 字符合“一般不超过 25 字”。

备选（只在老师允许改题时用）：

- 《面向直营品牌的新能源汽车配置与报价系统设计与实现》（25 字）
- 《基于服务端定价的新能源汽车在线配置系统设计与实现》（25 字）

论文里建议写“某新能源直营品牌（D 品牌）”；演示截图可保留比亚迪公开海报，但图注写明：图片来自比亚迪官网公开素材，仅用于毕业设计演示，本文与比亚迪无隶属或合作关系。

## 2. 论文定位

不要把论文写成“我做了哪些页面”。把问题收窄为三句话：

1. 汽车配置项之间存在互斥、依赖、版本门槛，普通商品 SKU 模型表达不了；
2. 落地价由裸车、购置税、保险、上牌、选装共同构成，必须服务端可复算；
3. 前端展示、报价单、订单快照必须同源，否则改价或刷新后会出现同配置不同价。

可以写的工作点：配置目录建模、规则校验、服务端定价、订单快照/状态机、图片化配置器、测试与部署。

不要写的伪创新：首次提出、填补空白、国内领先；不要把 Vue/Fastify/SQLite 本身当创新；不要把 3D 说成核心成果（已退出主路径）；不要编造问卷、并发或提升百分比。

## 3. 篇幅与章节分配

学校规范：理工类毕业论文不少于 12000 字；软件类毕业设计不少于 8000 字。按 12000 字准备，按毕业设计认定也稳。

| 部分 | 目标字数 |
|---|---:|
| 中文摘要 | 400–500 |
| Abstract | 约 300 英文实词 |
| 第1章 绪论 | 1500 |
| 第2章 相关技术与需求分析 | 2300 |
| 第3章 系统设计 | 3200 |
| 第4章 系统实现 | 3000 |
| 第5章 系统测试与结果分析 | 1700 |
| 结论 | 700 |
| 正文合计 | 约 12400 |

如果按 8000 字毕业设计认定，按上表压缩到 70%，但不要低于 8000。

## 4. 章节提纲

### 第1章 绪论（1500 字）

1.1 研究背景与意义：新能源汽车直营/线上下单趋势；配置复杂、价格不透明、前后端价格不一致；理论意义与实际意义。
1.2 国内外研究现状：国外产品配置器/CPQ/大规模定制；国内产品配置器与汽车在线配置实践；现有不足是制造端算法多、面向消费者官网的“配置—报价—订单”工程实现少。
1.3 研究内容：配置建模、规则校验、服务端定价、订单快照、图片化前台与验证。
1.4 研究方法与技术路线：文献研究、需求分析、原型迭代、自动化测试、线上部署；配图1-1。
1.5 论文结构：一段话交代第2–5章，不要复制目录。

写作提醒：研究内容用“本文开展……”的将来时/工作口吻；文献综述要归纳，不要逐篇摘要。

### 第5章 系统测试与结果分析（1700 字）

5.1 测试策略与环境：单元/接口/页面/部署冒烟；表5-1。
5.2 功能与接口测试：9 个测试文件 / 38 项（表5-2：健康、车型、报价、订单、认证、后台、试驾、新闻、种子）；关键断言：服务端计算、非法组合 400、订单快照、幂等支付、权限。

5.5 安全与边界：服务端权威、参数校验、Cookie、SQL 注入防护、订单越权检查；明确未做 CSP、真实支付、压力测试、第三方渗透。
5.6 本章小结。

### 结论（700 字，不编号）

完成了什么：系统 + 配置规则 + 服务端定价 + 订单快照 + 图片化前台 + 测试/部署。
解决了什么：配置组合可校验、价格可复算、订单可追溯。
不足：车型少、模拟支付、单机 SQLite、图片非白底实拍、无 CSP。
展望：更多车型、真实支付、对象存储/CDN、可配置规则引擎、用户可用性实验。

学校规范：结论单独排写，不加章标题序号，不标引用文献，400–1000 字。

## 5. 摘要初稿（约 420 字）

针对新能源汽车直营模式下车型配置组合多、选装规则复杂、落地价构成不透明的问题，设计并实现了一个新能源汽车在线配置与报价系统。系统采用前后端分离架构，前端使用 Vue 3 与 TypeScript 构建响应式官网，后端使用 Fastify 提供 REST 接口，SQLite 保存车型、配置、订单与用户数据；前后端共享类型与定价逻辑。系统以服务端为唯一价格权威：前端只提交选项标识，服务端重新加载配置目录、校验选项归属与互斥/依赖/版本门槛，并按裸车、购置税、保险、上牌逐项计算落地价，金额统一以整数分存储。下单时保存配置与价格快照，支付接口采用幂等设计，订单状态机覆盖待支付、已支付、已确认、已交付与取消。前台提供车型矩阵、图片化配置器、报价单、下订、支付、订单、门店、试驾、账户与后台管理等功能，并完成 1440、1024、390 三档响应式适配与 HTTPS 部署。测试结果表明，系统 38 项 API 测试全部通过，配置规则、报价计算、订单快照与支付幂等符合预期，能够支撑毕业设计演示与后续扩展。

关键词：新能源汽车；在线配置；服务端定价；订单快照；Vue 3；Fastify

### Abstract

To address the problems of complex vehicle configuration combinations, complicated option rules, and opaque final prices in the direct-sales model of new energy vehicles, this thesis designs and implements an online configuration and quotation system. The system adopts a front-end and back-end separated architecture. The front end is built with Vue 3 and TypeScript as a responsive official website, while the back end uses Fastify to provide REST APIs and SQLite to store vehicle, configuration, order, and user data. Types and pricing logic are shared between the front end and back end. The server is the single source of price authority: the client submits only option identifiers, and the server reloads the configuration catalog, validates option ownership, mutual exclusion, dependencies, and trim thresholds, and calculates the final price from the vehicle price, purchase tax, insurance, and registration fee. All amounts are stored as integer cents. When an order is created, a snapshot of the configuration and price is persisted; the payment API is idempotent, and the order state machine covers pending payment, paid, confirmed, delivered, and cancelled. The system provides a vehicle matrix, an image-based configurator, quotation, ordering, payment, order tracking, stores, test drives, user account, and an admin console, with responsive layouts at 1440, 1024, and 390 pixels and HTTPS deployment. Test results show that all 38 API tests pass and that configuration rules, quotation, order snapshots, and payment idempotency meet the design expectations.

Keywords: new energy vehicle; online configuration; server-side pricing; order snapshot; Vue 3; Fastify

## 10. 答辩怎么讲

30 秒：题目 + 问题（配置约束/价格透明/订单一致）+ 系统已上线。
2 分钟：演示“选车 → 配置 → 报价 → 下订 → 支付 → 后台”。
3 分钟：讲三个设计点（目录/规则、服务端定价、订单快照）。
2 分钟：测试 + 部署 + 不足。
预留 Q&A：为什么不用 3D？为什么 SQLite？怎么防前端改价？订单快照解决什么？38 项测试覆盖什么？

论文每一章都要能回答答辩的一个问题，不要在正文里写演示脚本。

## 11. 最容易翻车的 6 件事

1. 把论文写成功能清单，每章都在说“我做了页面”，没有设计取舍。
2. 前后端价格都算；论文必须明确服务端唯一权威，前端只展示。
3. 订单不存快照；只存 modelId/optionIds，改价后历史订单对不上。
4. 参考文献凑数；15 篇里至少 7 篇期刊、外文 3 篇、近 5 年 1/3，逐条核。
5. 图表没有来源/图题；截图、E-R、架构图都要编号，文中先引用。
6. 品牌/版权；论文用“某新能源直营品牌”，截图加“非官方、仅教学演示”。
